# Embedding Maestro-Studio-Style Device Mirroring & Tap Recording in a VS Code Extension

## TL;DR
- **Do not try to reuse `maestro studio` as a live backend for a distributable extension.** The interactive Studio today is the **closed-source Maestro Studio Desktop app**; the older open-source browser server (Ktor, `package maestro.studio`, class `DeviceScreenService`, port 9999) was **removed from the CLI in Maestro v2.6.0** ("The web-based Maestro Studio that shipped inside the CLI has been removed… use the standalone Maestro Studio desktop app"). You can still reuse Maestro's **Apache-2.0 driver stack** (`maestro-client`, `dadb`, the Android instrumentation APK, the iOS XCTest runner) as a sidecar, but there is no documented, stable local API to attach to.
- **Best architecture: run a Node/TypeScript sidecar that mirrors the device with scrcpy (Android) and WDA-MJPEG / simctl (iOS), render frames in a webview `<canvas>` via WebCodecs (video) or an `<img>`/canvas MJPEG loop (screenshots), and capture taps in the webview** — translating click coordinates back to `tapOn: {point}` or, after a hierarchy lookup, element-based `tapOn: {text/id}`. This is exactly how `ws-scrcpy`, `scrcpy-vscode`, and Appium Inspector are built.
- **Real-time video mirroring (scrcpy / WDA-MJPEG) is the right default for a fluid recorder;** periodic screenshots are simpler and are what Appium Inspector/Maestro use for element inspection, but are too laggy for smooth interaction. Use **video for the live view, plus a screenshot + hierarchy snapshot on each tap** for element resolution.

## Key Findings

### 1. Maestro internals & reusability
- Maestro is a layered Kotlin/JVM system: CLI → Orchestra (command engine) → `maestro-client` (`Maestro.kt`, `Driver.kt`) → platform drivers (`AndroidDriver.kt`, `IOSDriver.kt`, `WebDriver.kt`). It is Apache-2.0.
- **Android:** The CLI installs a `maestro-server.apk` (an instrumentation APK started via `adb instrument`) that runs an on-device **Netty gRPC server**; that server uses **UIAutomator** to dump the view hierarchy as XML and to perform actions. The CLI also uses raw `adb` commands for some interactions and **pulls screenshots on a short interval**, doing image comparisons to detect when the screen has "settled."
- **iOS:** `IOSDriver` talks over **HTTP to an XCTest-based driver** (a WebDriverAgent-like `maestro-driver-ios` XCUITest runner). Element hierarchy comes from XCUITest; the runner exposes an HTTP server (the community real-device port uses device port 22087).
- Maestro's element model uses the **accessibility tree** (the same layer screen readers like VoiceOver/TalkBack use) on both platforms, which is why `tapOn: "text"` / `tapOn: {id}` works across native, React Native, Flutter, and hybrid apps.
- **Reusable libraries:** `dadb` (Apache-2.0 Kotlin library to talk to an Android device without an adb binary/server) and `maestro-client` (published to Maven Central as `dev.mobile:maestro-client`) are genuinely reusable as a JVM sidecar. You could run a small Kotlin process that embeds `maestro-client`, exposes your own stdio/WebSocket protocol, and lets your Node extension drive taps and pull hierarchy — reusing Maestro's driver logic without reverse-engineering Studio.
- **Studio API status:** The open-source `maestro studio` served a Ktor app on `http://localhost:9999` (confirmed via GitHub-issue stack traces naming `maestro.studio.DeviceScreenService` and server logs "Responding at http://0.0.0.0:9999"). It served the device screenshot + view-hierarchy JSON and an interaction/REPL route, but it was **never a documented/stable API** — path strings and line numbers shifted between releases — and it was **removed from the CLI in v2.6.0** (current CLI is v2.8.0) in favor of the closed-source desktop app and a new "Maestro Viewer." Reverse-engineering would require pinning an older Maestro git tag. **Recommendation: don't depend on it.**

### 2. Android specifics
- **Screen mirroring — use scrcpy.** scrcpy (Genymobile, Apache-2.0, **actively maintained — v3.3.4 released 17 Dec 2025**, ~148k GitHub stars) pushes a `scrcpy-server.jar` to the device via adb and streams **raw H.264/H.265/AV1** over an adb-tunneled socket, plus separate audio and control sockets. You can consume this stream programmatically: `ws-scrcpy`, `ws-scrcpy-web`, and `scrcpy-vscode` all push the vanilla scrcpy server, demux its sockets, and decode video in the browser via **WebCodecs** (hardware-accelerated). This is the modern, maintained path and works on emulators and real devices.
- **minicap/minitouch (OpenSTF/DeviceFarmer) are effectively legacy.** They rely on private AOSP APIs and native libs that break on each Android release; OpenSTF's last release maxes out at Android 9, DeviceFarmer's fork lags Android 14/15, and minicap explicitly "does not support emulators." Prefer scrcpy.
- **Simpler options:** `adb exec-out screencap -p` (one-off PNG screenshots, fine for a periodic-screenshot mode) and `adb shell screenrecord` (H.264 to file, ~3-min cap, high latency — poor for interactive mirroring).
- **Injecting taps:** `adb shell input tap x y` (simple, higher latency) or scrcpy's control socket (low latency — what scrcpy-based tools use). Maestro uses UIAutomator + adb.
- **Capturing REAL user taps on the device** (as opposed to injecting) is the hard part and there is **no clean public Android API** — apps can't observe global touches since Android 4.1. Options wrap `adb shell getevent` (reads `/dev/input/eventX`, gives raw multitouch `ABS_MT_*` events you must scale from device input space to screen pixels; timestamped with `-t`): `android-touchlogger`, `adb-event-record`, `geteventplayback` (some need root). **However, for a Maestro-style recorder you generally should NOT capture on-device taps at all** — you capture clicks *in your mirrored webview* (where you already know x/y in image space) and inject them to the device. That sidesteps getevent entirely.
- **UI hierarchy:** `uiautomator dump` (or UIAutomator via an instrumentation server, as Maestro does) gives an XML tree with bounds / resource-id / text / content-desc for element-based recording.

### 3. iOS specifics
- **idb (facebook/idb) is essentially unmaintained.** Appium's `appium-idb` is explicitly marked: "Deprecated: appium-idb is no longer actively maintained. The upstream fb-idb stack is not maintained well, and Appium is moving to homegrown, properly maintained clients for private Apple APIs (like, appium-ios-remotexpc)." idb still had open issues into late 2025 but no meaningful maintenance. **Do not build on idb.**
- **Current recommended iOS stack:** **WebDriverAgent (WDA)** — the appium/WebDriverAgent fork is the actively-maintained one — plus **`pymobiledevice3`** (pure-Python, actively maintained, supports iOS 17+ tunnels/DDI) or **`go-ios`** for device discovery, port forwarding, app install, and DVT/DDI services; `libimobiledevice`/`iproxy` for USB port forwarding.
- **Mirroring the iOS Simulator:** `xcrun simctl io booted screenshot out.png` (periodic screenshots) and `xcrun simctl io booted recordVideo out.mp4` (records to file; you SIGINT to stop — **not** a low-latency stream). There is **no official low-latency simulator streaming API**; for a live view, either poll screenshots quickly or run WDA in the simulator and consume its **MJPEG server** (default port 9100; override on simulators via `SIMCTL_CHILD_MJPEG_SERVER_PORT`).
- **Mirroring a REAL iOS device:** the classic route is the **CoreMediaIO DAL / AVFoundation** path — the same mechanism QuickTime/OBS use. You must opt in via `kCMIOHardwarePropertyAllowScreenCaptureDevices`, then the device appears as an `AVCaptureDevice` (`.muxed`) you can capture (macOS-only, native code). Alternatively, **WDA's MJPEG server on port 9100** (forward with `iproxy 9100:9100`) gives an MJPEG frame stream cross-platform without native code — this is what Appium / ws-scrcpy / Midscene use. `go-ios` / `pymobiledevice3` can also grab frames.
- **Injecting/capturing taps on iOS:** **WDA** (W3C WebDriver, `/wda/touch/perform`, port 8100) is the practical option for both simulators and real devices; XCUITest underlies it. For simulators only, some tools use `simctl`. There is **no way to passively capture a user's real finger taps** on a physical iPhone due to sandboxing — again, capture clicks in your mirrored webview and inject via WDA.
- **Maestro real iOS device support:** Officially, Maestro **does not natively support physical iOS devices** — only iOS Simulators (plus cloud real devices). Per DeviceLab (Dec 2025), it supports Android simulators+real devices and iOS simulators, but **not** iOS real devices. Real-device support has been "one of Maestro's most requested features since January 2023." Community PR **#2856 ("feat: Add iOS physical device support"), authored by omnarayan (Om Narayan) of DeviceLab**, plus their `maestro-ios-device` tool, add it by building/deploying the XCTest runner to hardware (needs an Apple Developer cert + Developer Mode) and forwarding `localhost:6001 → device:22087`. DeviceLab notes "The Maestro team has indicated official iOS real device support won't land until next year. No committed timeline." Some commands (`addMedia`, `setLocation`) are limited/unsupported on real devices due to Apple restrictions. The tool is "an unofficial community tool. Not supported by mobile.dev or the Maestro team" (tested on iOS 16.x–18.x and 26.x).

### 4. Architecture recommendation for the VS Code extension
- **Process model:** VS Code extension host (Node/TS) spawns a **sidecar** (either scrcpy + your own adb/WDA glue in Node, or a small JVM process embedding `maestro-client`/`dadb`). The webview panel is pure HTML/JS and communicates with the extension host via `postMessage`.
- **Video path (recommended default):** sidecar pushes scrcpy-server (Android) / consumes WDA-MJPEG or CoreMediaIO (iOS), forwards frames to the webview over a WebSocket (or via `postMessage` for MJPEG). In the webview, decode H.264 with **WebCodecs `VideoDecoder`** and draw to a `<canvas>`; for MJPEG just swap an `<img>`/canvas per frame. `scrcpy-vscode` (izantech) already does exactly this — its changelog states "Real-time screen mirroring using WebCodecs API for hardware-accelerated decoding" inside a VS Code webview, with "Touch input support including tap, drag, and mouse wheel scrolling" (and it trimmed the shipped package from 717 KB to 134 KB).
- **Screenshot path (fallback / element inspection):** poll `adb exec-out screencap` / `simctl io screenshot` / WDA screenshot; simpler, lower FPS, fine for a "tap-to-inspect" mode.
- **Tap capture & recording:** listen for `click`/`pointerdown` on the canvas; convert canvas coords → device pixel coords (scale factor = device resolution / rendered size). Then either (a) emit a coordinate step `tapOn: {point: "x,y"}` (Maestro supports absolute px or percentages like `"50%,50%"`), or (b) fetch the current hierarchy (uiautomator / XCUITest), hit-test which element contains the point, and emit the more robust element step `tapOn: {text: ...}` / `tapOn: {id: ...}` — mirroring how Appium Inspector clicks a screenshot then resolves attributes. **Percentage coordinates are more device-independent than absolute px.**
- **Reference implementations to study:** `ws-scrcpy` (NetrisTV) and `ws-scrcpy-web` (bilbospocketses) — browser mirroring + control for Android, with limited iOS via WDA/ws-qvh; `scrcpy-vscode` and sibling VS Code scrcpy extensions — webview + WebCodecs + touch injection already working in VS Code; **Appium Inspector** — screenshot + XML hierarchy + click-to-locator + record-to-script, the closest analog to what you're building; Midscene (iOS via WDA MJPEG + WebDriver). Flutter/React Native "device preview" features run *in-app* and are not a device-mirroring model, so they're less relevant.

### 5. Licensing
- **Maestro:** Apache-2.0 — safe to embed/adapt (`maestro-client`, `dadb`, orchestra, the driver APK/XCTest runner). Note the **Studio Desktop app is NOT open source** and cannot be reused/embedded.
- **scrcpy:** Apache-2.0 — safe to bundle the `scrcpy-server.jar` and client logic. (This is why ws-scrcpy/scrcpy-vscode can ship it.)
- **WebDriverAgent / Appium components:** Apache-2.0 — safe.
- **idb:** permissive (Facebook) but effectively abandoned — avoid.
- **minicap/minitouch:** Apache-2.0 but legacy/unmaintained — avoid.
- **pymobiledevice3:** actively maintained, permissive — usable, but adds a Python runtime dependency.
- Bundling native binaries (scrcpy, adb, iproxy) in a VS Code extension is fine license-wise but increases package size and requires per-platform binaries; prefer detecting user-installed tools where possible.

## Details

**Why not attach to `maestro studio`:** Even in versions where the Ktor server on :9999 existed, it was an internal browser↔server contract with shifting line numbers/paths across releases, no OpenAPI/docs, and it's now removed from the CLI (v2.6.0). Building a distributable product on it would be fragile. The durable reuse story is the Apache-2.0 **driver layer**, not Studio.

**Android decision:** scrcpy for the live mirror (WebCodecs decode in webview), `uiautomator dump` or a Maestro-style instrumentation server for hierarchy, and inject taps via scrcpy's control socket or `adb input`. Avoid minicap/minitouch.

**iOS decision:** Simulators are easy (simctl screenshots for inspection, WDA for control / MJPEG for a smoother view). Real devices are the hard case: use WDA (control on 8100 + MJPEG on 9100) with `pymobiledevice3` / `go-ios` / `iproxy` for tunneling, or CoreMediaIO/AVFoundation for the highest-fidelity mirror (macOS-native code). Expect provisioning / Developer-Mode friction.

**Recording model:** Always capture interactions in your mirrored view, never from on-device touch capture (getevent / global touch listeners are root-y, brittle, and impossible on iOS). Resolve taps to elements via a hierarchy snapshot for robust `tapOn` selectors, falling back to coordinates.

## Recommendations
1. **Phase 1 (Android + emulators, fastest win):** Ship scrcpy-based mirroring in a webview (fork/study `scrcpy-vscode`), capture canvas clicks, emit coordinate-based `tapOn`. Add `uiautomator dump` hit-testing for element-based selectors.
2. **Phase 2 (Android real devices):** Same path — scrcpy already handles real devices over adb. Add a device picker.
3. **Phase 3 (iOS Simulator):** WDA in the simulator for control + hierarchy; simctl screenshots or WDA-MJPEG for the view.
4. **Phase 4 (iOS real devices):** WDA + pymobiledevice3/go-ios tunneling; consider CoreMediaIO for a high-quality mirror if you can ship macOS-native code. Budget for provisioning/cert UX.
5. **Reuse decision:** If you want Maestro-compatible YAML and selector semantics, embed `maestro-client`/`dadb` (Apache-2.0) in a JVM sidecar rather than reverse-engineering Studio.
6. **Benchmarks that change the plan:** if official Maestro iOS real-device support ships, switch to it; if scrcpy adds/removes codecs, adjust the WebCodecs decoder; if you need >30 FPS smoothness, prefer video over screenshots.

## Caveats
- The closed-source status of Maestro Studio Desktop and the removal of the OSS :9999 server (v2.6.0) are the biggest constraints; verify against the current Maestro CHANGELOG at integration time.
- iOS real-device support in Maestro is community/unofficial today and may break with Maestro releases.
- CoreMediaIO/AVFoundation device capture is macOS-only and needs native code; MJPEG via WDA is the cross-platform fallback but heavier per-frame.
- getevent-based touch capture generally needs root and coordinate scaling; avoid it in favor of webview-side capture.
- Bundling binaries raises extension size and per-OS packaging complexity.
- The exact open-source Studio endpoint path strings (e.g., `/api/device-screen`, `/api/hierarchy`, `/api/interact`) could not be verbatim-confirmed from source in this research; the class `DeviceScreenService`, the Ktor framework, and port 9999 are confirmed, but if you ever do reverse-engineer them, read them from a pinned pre-2.6.0 tag of `mobile-dev-inc/Maestro` (module `maestro-studio/server`, package `maestro.studio`).
